# Billing: listers cancel and delete unpaid invoices

## Goal

On **Account → Subscription & billing** (`/account/billing`), let a lister who manages the plan:

1. **Cancel** an open (unpaid) listing-plan invoice they started but did not finish paying.
2. **Delete** (remove from their list) an invoice that is already cancelled/void, whether they
   cancelled it or the system voided it (plan switch, scheduled downgrade).

Paid and refunded invoices can never be cancelled or deleted.

## Decisions and assumptions

1. **Cancel = void.** Cancelling sets the invoice to `void` with `voidedAt` (reuses `voidInvoices`).
   No new invoice status. In the lister UI the `void` label becomes **"Cancelled"**.
2. **Delete = hide from the lister, not a hard delete.** Invoices are referenced by `payments`,
   append-only `payment_events` and `billing_audit_log`, so rows cannot (and must not) be removed.
   Add a nullable `lister_hidden_at` timestamp on `invoices`; `listInvoices` excludes hidden rows.
   Admin billing screens are unchanged and still show every invoice.
3. **Delete only where no money moved**: status `void` **and** no payment on it in
   `confirmed | flagged | refunded | credited`. A void invoice with a flagged late payment stays
   visible (the lister may need it for a refund conversation).
4. **Cancel is refused while a payment may still land**:
   - an STK push on the invoice still `pending` and created within `IN_FLIGHT_SECONDS` (90 s);
   - a card payment still `pending` and created within `CARD_CANCEL_BLOCK_MINUTES` (15 min).
   Message: "A payment for this invoice is still in progress. Try again in a few minutes."
   Older pending payments don't block; if one ever confirms, the existing confirm path flags it
   (`invoice_not_open`) for admin refund — nothing activates.
5. **Never-paid subscription**: if the cancelled invoice belongs to a `pending` subscription and
   it now has no open invoices, the subscription moves to `cancelled` with `cancelledAt = now`
   in the same transaction. The plan card then shows "No listing plan yet / Choose a plan".
   Active, grace or paused subscriptions are untouched (only the renewal/upgrade invoice is voided).
6. **Who**: only users with `canManage` (own pool, or agency admin). Agency members see no actions.
7. **Scope**: listing-plan invoices only — the invoices table shows nothing else. Verification
   invoices (VerificationCard flow) are out of scope.
8. **Audit**: cancelling appends a `payment_events` row (`event_type = 'invoice_cancelled'`,
   `invoice_id`, payload `{ by: "lister", subscriptionCancelled: boolean }`, no personal data).
   Hiding is a display preference, not a status change: no event.
9. **No rate limit**: each action is one session-scoped update of the user's own rows with no
   external call; repeat submits are idempotent. (Revisit if abuse appears.)
10. Actions identify the invoice by **invoice number** (what the UI already shows), validated as
    `^VPK[0-9]{7,9}$`; ownership is re-checked on the server.

## Implementation requirements

### Domain (`invoice-actions.ts`)

`cancelInvoice` — one transaction via `deps.withTransaction`:
1. Resolve the pool (`getListingPool`); if agency pool and not agency admin → `forbidden`.
2. Lock the invoice `FOR UPDATE` by number, joined to a `listing` subscription owned by the pool;
   none → `not_found` (same result for another user's invoice; never reveal existence).
3. Status `void` → `ok` (idempotent, no new event). Status `paid`/`refunded` → `not_cancellable`.
4. Load its payments; `cancelBlock(...)` → `in_progress` when blocked.
5. `voidInvoices(tx, [id], now)`; append the `invoice_cancelled` event.
6. Lock the subscription; if `pending` and `openInvoices` is now empty → `cancelled`, `cancelledAt`.

`hideInvoice` — one transaction: same ownership/permission lookup; status must be `void` and
`canHide` true, else `not_deletable`; set `listerHiddenAt = now` (idempotent if already set).

Result type: `{ ok: true; subscriptionCancelled?: boolean } | { ok: false; code: "not_found" | "forbidden" | "not_cancellable" | "in_progress" | "not_deletable" }`.

### Server Actions (`actions.ts`)

- `cancelInvoiceAction(formData)` / `deleteInvoiceAction(formData)`: `requireLister`, Zod-parse
  `invoiceNumber`, call the domain function in try/catch (`logFailure`, no internals leaked),
  `redirect` to `/account/billing?updated=invoice_cancelled|invoice_deleted` or
  `?error=invoice_in_progress|invoice_failed`.
- Flash copy (page `FLASH` map):
  - `invoice_cancelled`: "Invoice cancelled. Don't pay it by Paybill; start a new payment when you're ready."
  - `invoice_deleted`: "Invoice removed from your list."
  - `invoice_in_progress`: "A payment for this invoice is still in progress. Try again in a few minutes."
  - `invoice_failed`: "We couldn't update that invoice. Please try again."

### UI

`InvoiceTable` receives `canManage`. The existing last column (receipt) becomes an actions cell:

- **paid**: "Receipt" link (unchanged).
- **open** + `canManage`: `<details>` disclosure **"Cancel"** → micro text "This invoice can't be
  paid after you cancel it." → destructive-styled submit **"Yes, cancel invoice"**.
- **void** + `canDelete` + `canManage`: `<details>` **"Delete"** → micro text "It's removed from
  your list. Our payment records keep it." → submit **"Yes, delete"**.
- Status labels: `void` → "Cancelled" (`text-slate-600`).
- Each form posts a hidden `invoiceNumber`; submit buttons use `useFormStatus` pending state
  (disabled + Spinner) in a small client component; everything else stays server-rendered.
- The Paybill instructions panel disappears automatically once no open invoice remains.

Tokens and sizes (compact system, `prompts/ui-compact-design-system.md`, `ui-mobile-optimization.md`):
- Summary trigger: `text-small font-medium`, `min-h-control` (44 px) on mobile cards; in the md+
  table `h-control-sm` (32 px) with 44 px hit area via padding where space allows.
  Cancel trigger text `text-ink`, Delete trigger `text-slate-700`; `hover:bg-white` on the canvas row.
- Confirm buttons: existing `Button` with `variant="secondary"` (or the kit's danger variant if it
  exists), `size` default (`h-control`), `rounded-lg`. No new colours; warning copy `text-slate-700 text-micro`.
- No shadows, no popovers, no `text-base/lg/xl`. Disclosure content opens below the trigger inside
  the cell (table) or at the bottom of the card (mobile), full-width on < 640 px.
- `aria`: summary text includes `<span className="sr-only"> invoice VPKxxxxxxx</span>`; the
  disclosure chevron is `aria-hidden`.

## Security requirements

- Session required (`requireLister`); only `canManage` users may act; ownership re-checked in the
  locked query, scoped by pool + `kind = 'listing'`. Other users' invoice numbers return `not_found`.
- Client sends only `invoiceNumber`; no ids, amounts or statuses are trusted from the browser.
- Paid/refunded invoices and anything with money attached are never voided or hidden.
- `payment_events` stays append-only; invoice terms trigger untouched; no hard deletes.
- Logs carry the error name only; no phone numbers or invoice payloads.

## Acceptance criteria

1. An open invoice shows "Cancel"; confirming voids it, shows the success flash, the row reads
   "Cancelled", and the Paybill panel for it is gone.
2. Cancelling the only invoice of a never-paid plan leaves "No listing plan yet / Choose a plan";
   choosing a plan afterwards creates a fresh pending subscription and invoice normally.
3. Cancelling a renewal/upgrade invoice on an active plan leaves the plan, period and listings unchanged.
4. Cancel within 90 s of an STK push (or 15 min of a pending card payment) is refused with the
   in-progress message; the invoice stays open.
5. A cancelled/void invoice with no money shows "Delete"; confirming removes it from the list; it
   still appears in admin billing.
6. A void invoice with a flagged/refunded/credited payment shows no Delete; paid rows show only Receipt.
7. Agency members (non-admin) see no Cancel/Delete; a crafted POST from them returns the failure flash, nothing changes.
8. Submitting another lister's invoice number changes nothing.
9. Repeated submits are idempotent (one `invoice_cancelled` event).
10. A Paybill/STK payment that lands on a cancelled invoice is flagged, never activates (existing behaviour, covered by a test).

## Manual test steps (after implementation)

1. `npm run db:migrate`, then `npm run dev`.
2. Sign in as a lister with no plan → **Choose a plan** → pick a plan → start M-Pesa (sandbox) or
   just leave checkout so an open invoice exists. Wait > 90 s.
3. Go to `/account/billing`: the invoice shows **Open** and **Cancel**. Open it, read the warning,
   click **Yes, cancel invoice** → success flash, row says **Cancelled**, plan card says
   "No listing plan yet", Paybill panel gone.
4. On the same row click **Delete → Yes, delete** → "Invoice removed from your list."; the row is gone.
   Sign in as admin → `/admin/billing` → search the invoice number: it is still there, status void.
5. Start a new payment and immediately try **Cancel** (< 90 s) → in-progress message, still Open.
6. With an active plan, start a renewal, leave it unpaid, cancel it → plan and renewal date unchanged.
7. Sign in as an agency member (non-admin) → no Cancel/Delete buttons.
8. Repeat steps 3–4 at 390 px width (and on your phone) — disclosures open inline, buttons are 44 px.
